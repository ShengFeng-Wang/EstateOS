# Known Limitations

Claude Code records engineering caveats and deferred work here as they arise. Not for product/design ambiguities — those go in `docs/handoff/questions-for-codex.md`.

## Backend

- **`Microsoft.OpenApi` NU1903 advisory (high severity, GHSA-v5pm-xwqc-g5wc).** `Microsoft.AspNetCore.OpenApi 10.0.10/10.0.11` (the latest stable on .NET 10 as of 2026-08-25) depends on `Microsoft.OpenApi 2.x`, and every 2.x release carries this advisory; pinning `Microsoft.OpenApi` to a patched 3.x release breaks `Microsoft.AspNetCore.OpenApi`'s source generator (`IOpenApiMediaType.Example` becomes read-only, build fails). The vulnerability is in OpenAPI schema/example parsing used by the dev-time `/openapi` document generator, not in request handling. Left unpinned for now; revisit when Microsoft ships an `Microsoft.AspNetCore.OpenApi` build compatible with a patched `Microsoft.OpenApi`.
- Contract "one overlapping Active contract per property" and date-range validity are enforced in the `ContractService` application layer (interval-overlap queries), not as a database constraint — Postgres exclusion constraints could enforce this at the DB layer too but weren't added to keep the schema comprehensible per the implementation brief's guidance against over-engineering.
- Seed data (`DbSeeder`) only runs when `ASPNETCORE_ENVIRONMENT=Development` and only if `Users`/`Properties` are empty; it is not wired for a fresh production-style bring-up path yet.

## Frontend

- `/login`, `/overview`, `/properties`, `/properties/:id`, `/tenants`, `/tenants/:id`, `/contracts`, `/payments`, `/maintenance`, and `/digital-twin` are all wired to real API calls — every module in the brief's persistence model now has at least a List screen, and Properties/Tenants have Detail screens too. Login and the Properties List are pixel-matched to the approved Figma frames via the MCP connection; Property Detail, Tenant Detail, and the Contracts/Payments/Maintenance list screens (added 2026-08-26) follow the written component spec and established design tokens instead, since the Figma MCP connection was unavailable that session — see `docs/handoff/spec-deviations.md`.
- Contracts, Payments, and Maintenance have List screens only — no dedicated Detail screen yet (their rows link into the related Property Detail's tabs instead, which already surface the same record). Properties now have Create (`/properties/new`) and Edit (`/properties/:id/edit`) forms with React Hook Form + Zod validation; Tenants/Contracts/Payments/Maintenance still have no Create or Edit forms — they can only be created via the API directly, not the UI. This is the next gap to close per the brief's delivery order.
- Property Detail's Tenant tab, and the new Tenant Detail's "Current Lease" section, only surface the current lease (Active contract, or the most recent by start date) — there is no tenant/property lease history view across past contracts yet.
- The Contracts/Payments/Maintenance list screens denormalize `propertyCode`/`propertyName`/`tenantName` onto their DTOs (via an EF `Include` join) so the tables can show human-readable references instead of raw GUIDs — this was a backend change made alongside the frontend work, not present in the original brief's DTO shapes.
- Build size: the production bundle is ~1.4 MB (gzip ~401 KB) as of the Overview dashboard addition, mostly `three`/`@react-three/fiber`/`@react-three/drei`. `/digital-twin` and the Login 3D scene are the only two consumers; the Login scene's own component is lazy-loaded (`LoginSpatialCity` is a separate ~2.4 KB chunk), but three/R3F/drei themselves are still in the main bundle since `/digital-twin` isn't code-split. Consider lazy-loading the `/digital-twin` route with `React.lazy` if initial load time becomes a concern.
- **Executive Overview dashboard** (`/overview`, rebuilt 2026-08-26): KPI tiles, revenue trend, status distribution, and portfolio composition are all real data from `/api/dashboard/summary` and `/api/dashboard/trends`. The **occupancy trend chart is illustrative, not measured** — the schema has no historical occupancy time series (occupancy is a live property-status snapshot), so `mockOccupancyTrend()` in `OverviewPage.tsx` deterministically derives a plausible 6-month line around the current rate. The chart is labeled "Illustrative" in its subtitle so it isn't presented as real. No date-range control exists yet — the trend charts are hardcoded to the last 6 months (the brief's screen inventory calls for a "Date Range Changed" state that isn't built). Building a real occupancy trend would need a periodic snapshot table, which wasn't added given no product decision has been made on retention/granularity.
- Dashboard charts (`components/charts/`) are hand-built inline SVG/CSS, not a charting library — reuses existing design tokens only (no new categorical palette was introduced; the status-semantic colors already used in `StatusBadge` were validated for this use with `dataviz` skill's palette checker before reuse).
- **Dashboard motion pass (2026-08-27):** KPI tiles count up on load/change (`useCountUp`), line charts draw in with a crosshair/tooltip already present, and bar charts grow their fills in with a per-row stagger — all skip straight to the resolved state under `prefers-reduced-motion`. Requested directly ("更多用到動態的圖表動作").
- **Localization (2026-08-27):** requested directly ("加上轉換語言的按鈕... 繁體中文跟英文"). Built a lightweight custom i18n layer (`frontend/src/i18n/`) — a Zustand-persisted `locale` ('en' | 'zh-TW'), a flat `useTranslation()` dictionary hook, and `Intl`-based date/currency/number formatters — rather than adding a library (i18next etc. isn't in the brief's stack list). A `LanguageSwitcher` sits in the sidebar footer. Translation coverage matches `estateos-responsive-localization-spec.md`'s explicitly required frame set: Login, Sidebar/nav, Overview (incl. chart labels and month names), Properties List, Property Detail (all 5 tabs), Create/Edit Property, and Payments List — plus the shared `Pagination` component. **Not yet translated**: Tenants, Contracts, and Maintenance list/detail screens, the Digital Twin's in-canvas UI (toolbar/legend/selection panel), and all toast/validation copy outside the Property form — these remain English-only regardless of the selected language, which is an inconsistent experience in zh-TW today. Extending coverage to those screens is mechanical (same `t.*` pattern) but wasn't done this pass to keep scope bounded.

## Digital Twin (`/digital-twin`, added 2026-08-25)

Built per `docs/estateos/claude-threejs-implementation-spec.md`. Core scene, layout, materials, camera state machine, interaction, filters/modes, a11y, and loading/error/fallback states are implemented and manually verified (see `docs/handoff/test-report.md`). Deferred against the full spec:

- **No `EffectComposer`/`OutlinePass`.** Selection is communicated via the ground-plane ring geometry the spec explicitly allows as an alternative ("outline/ring instead of recoloring"), plus the hover emissive boost. If a future pass wants the crisper edge-outline look from the reference concept art, `OutlinePass` would need to be added (no new dependency required — it ships with `three`).
- **Facade detail (window/reveal lines, curtain-grid) is not implemented.** Each archetype gets one structural cue (stepped roof, crown band, split volumes, entry notch) instead of the instanced facade module lines the spec describes. Draw calls are comfortably within the High-tier budget (180) at the current 60-property scale without this detail or `InstancedMesh`; both should be revisited if the portfolio grows toward the spec's 200-property upper bound.
- **No dev-only diagnostics adapter** (property ID / world position / camera mode / quality tier / draw-call count). FPS and draw-call numbers were not formally benchmarked against the spec's "10-second representative run" acceptance criterion — only visually inspected during manual testing.
- **Assembly choreography is simplified**: buildings rise with a district/index-staggered cubic-out scale animation, but the six-stage timed sequence in the spec (grid draw-in, district anchor lines, facade resolve, status activation, toolbar-ready signal as separate timed phases) is not separately implemented — the overall effect (buildings emerging staggered by district) is present, the sub-second phase boundaries are not.
- **Camera transition duration is damping-based**, not an exact-seconds tween. `CameraControls`' `smoothTime` approximates the spec's ~0.72–0.85s targets rather than hitting them precisely.
- **Test coverage gap**: unit tests cover layout determinism/collision spacing, status/mode material mapping, and camera target/distance bounds. The spec's broader contract (Playwright suite as committed test files, WebGL context-loss fallback test, URL-hydration test, mobile first-tap test, quality-tier/reduced-motion unit tests) was exercised manually this session but not written as repeatable test files. See `docs/handoff/test-report.md`.
- **Occupancy percent is always `null`** — the API has no per-unit occupancy concept, so the label/panel correctly omit it (per the spec's "render null instead of inventing it") rather than showing a fabricated number.

## Real Map (`/digital-twin`, replaced the fictional Digital Twin 2026-08-27)

Requested directly by the product owner — see `docs/handoff/spec-deviations.md`'s 2026-08-27 entries for why this overrides the approved "not real GIS" spec. Built on `3d-tiles-renderer` (new dependency) against Google Maps Platform's Map Tiles API (Photorealistic 3D Tiles), verified live against Google's production servers (300+ successful tile requests) before shipping.

- **Requires `VITE_GOOGLE_MAPS_API_KEY`** in `frontend/.env` (gitignored, not committed — see `frontend/.env.example`). Without it, `/digital-twin` shows a clear "no key configured" message instead of a blank/broken canvas.
- **Scoped to a single zone — Bade (八德重劃區) — by direct request**, not the whole portfolio. `RealMapPage.tsx` filters to `city === 'Taoyuan' && district === 'Bade'` before anything reaches the scene; the other 8 seeded districts' properties never render here. A `GeoLeash` component (`features/real-map/GeoLeash.tsx`) additionally clamps the camera's straight-line distance from Bade's centroid on every `GlobeControls` change event, since the library has no built-in geographic pan bounds — dragging or scrolling far enough gets snapped back rather than letting the view wander to another city.
- **Buildings are clickable and show price/status/type/address** via `RealMapSelectionPanel` — restoring the old Digital Twin's click-to-inspect interaction on top of the real tiles. Since Google's Photorealistic 3D Tiles have no per-building pick metadata (it's a continuous photogrammetry mesh, not semantically diced buildings), each property gets an invisible cylindrical hit target sized from its floor area (`footprintRadius()` in `PropertyMarker.tsx`) positioned at its real coordinate — clicking near the real building selects the property it's a proxy for, not the actual mesh triangle under the cursor.
- **Non-Bade property markers are placed at district-centroid + deterministic jitter, not geocoded addresses.** The 9 districts in `DbSeeder.cs`'s seed data are mapped to their real lat/lng in `districtCoordinates.ts` (a small hand-maintained table, not surveyed to the readjustment-zone boundary specifically); each property's exact position is that centroid plus a stable ±0.006° jitter derived from its ID (reusing the Digital Twin's existing `seededRandom` utility). This is real geography at district granularity — it does not mean the fictional street address was geocoded, since that address doesn't exist. (Bade's own 5 properties are handled separately — see below.)
- **Bade's 5 properties are real, named buildings — not procedurally generated.** Per direct request, `SeedRealBadeProperties` in `DbSeeder.cs` seeds 5 real developments (城中大璽, 合遠首綻, 冠奕深耕13, 麗寶青年時代, 德億御邸) on their real roads, names/roads verified via web search against a public community listing (`community.houseprice.tw`). **Coordinates are approximate**: each building's real road is confirmed, but no geocoding tool was available to survey its exact plot, so `frontend/src/features/real-map/realBadeBuildings.ts` places each at a small, distinct offset within the real Bade Redevelopment Zone rather than a literal building-footprint-accurate GPS point. **Rents are estimates, not scraped listings**: the product owner initially asked to query a live rental site (591 or similar) for exact current prices; this was flagged as a real ToS/misrepresentation risk (republishing a real third party's real listing as this fictional company's managed property) and the owner chose the safer alternative instead — rents are grounded in 八德地政事務所's cited per-ping rent averages (via a news article) for relative tier ordering among these specific buildings, scaled into this app's existing Apartment/Townhouse rent bands for internal consistency with the rest of the seeded portfolio. See `docs/handoff/spec-deviations.md`'s second 2026-08-27 entry for the full reasoning.
- **Clickable footprints have a tall always-visible beacon + ground highlight** (`PropertyMarker.tsx`) colored by status. This took two passes: the first (ground wash only) was reported "太不明顯了" (still too subtle) since a flat ground disc shrinks to nothing at distance; a 160m vertical column was added but was *still* reported invisible — the actual bug was the column's radius (1.6m), far too thin to register at typical 400-900m viewing distances regardless of height. Fixed by widening it to 6m radius (9m cap sphere) and disabling `depthTest` on its material so it renders through any real building that would otherwise occlude it — confirmed visible in both the default zone view (all 5 beacons visible, color-coded by status) and up close after a fly-to.
- **A `BuildingList` panel lists all 5 Bade properties** (status-colored dot + name) in the top-left overlay; clicking one flies the camera there (`CameraFlyTo.tsx`, a ~1.1s eased position/orientation tween with `GlobeControls.enabled` toggled off mid-flight to prevent input fighting the transition) and opens its selection panel — requested directly: "然後要有一個列表 點哪一間 就跳至那一棟的地圖位置." Clicking a marker directly (not via the list) still just selects in place without flying, since the user already navigated there manually.
- **Occasional HTTP 400s on individual tile sub-requests are normal** at this dataset's LOD/quadtree boundaries — observed throughout testing (a small fraction of hundreds of successful requests) with no accompanying app error; `3d-tiles-renderer` skips the failed tile and the rest of the tileset loads and renders correctly. Distinct from the earlier `autoRefreshToken` bug, which caused an uncaught crash — this is silent, harmless request-level noise.
- **Google's photogrammetry mesh shows spike/shard artifacts on thin objects** (trees, lamp posts, thin railings) at close range — visible in testing during this session. This is an inherent, well-documented characteristic of Google's Photorealistic 3D Tiles dataset itself (present in Google Earth and every other viewer of this data), not an integration defect.
- **Session-token auth needs `autoRefreshToken: true`** on `GoogleCloudAuthPlugin` — without it, extended interaction (heavy panning/dragging) hit session-token expiry and threw an uncaught `TypeError` inside the plugin's error path, breaking tile loading entirely. Fixed during this session's own testing; flagged here in case a future upgrade of `3d-tiles-renderer` changes this option's behavior.
- **No quality-tier system, reduced-motion handling, or mobile/2D fallback yet** for this new map — the old Digital Twin's quality tiers, `prefers-reduced-motion` support, and WebGL-unsupported 2D list fallback were spec'd and built for the fictional city; the replacement only has a basic WebGL-support check and a loading/error state. GlobeControls' damping can also be disorienting for motion-sensitive users with no way to disable it yet.
- **No visualization modes, legend, or DOM keyboard-navigable asset list** — the old Digital Twin's occupancy/revenue/contract/maintenance color modes, `SpatialLegend`, and `AssetListMirror` (keyboard accessibility) have no equivalent here yet. Markers are always colored by status only, and there is no accessible non-canvas way to browse or select a property from this screen (status/type filters are moot now that the view is scoped to one district, but the accessibility gap remains).
- **The old fictional-city implementation is not deleted** (`frontend/src/features/digital-twin/`, its tests, `docs/estateos/claude-threejs-implementation-spec.md`) — kept as a rollback path since the new feature depends on an external billed API that hasn't been load- or cost-tested over time. See spec-deviations.md for how to roll back.
- **Cost/quota**: every tile fetch is a billed Google Maps Platform request. No usage monitoring or client-side request budget was added — the user should watch their Google Cloud Console billing/usage dashboard, especially during development where hot-reloads and repeated navigation to the page multiply requests.
